상태: 착수용 작업 명세. 아래 기능은 아직 구현되지 않았다.
저장소: https://github.com/sleepyJK/sc1BdOptimizer
기준: 2026-11-05 확인한 main의 README, HANDOFF 및 app.js
권장 브랜치: `feat/target-block-link`

## 1. 이번 작업의 목표

상대 뮤탈리스크 블록을 이동하거나 생산 시간을 바꾸면, 목표 시각과 내 대응 여유가 함께 바뀌도록 구현한다.

현재는 상대 블록과 목표 시각 숫자가 독립적이다. 예를 들어 뮤탈 완료를 05:30에서 05:45로 옮겨도 비교 기준은 05:30에 남는다. 이 불일치를 해결하는 것을 첫 작업으로 제안한다. 앱의 핵심인 양쪽 빌드 비교를 직접 개선하고, 실제 게임 데이터가 없어도 검증할 수 있다.

인수인계의 전체 모듈 분리는 후속 별도 PR로 진행한다. 이번 작업에는 시간 비교 계산을 테스트할 수 있는 최소 분리만 포함한다.

## 2. 착수 순서

1. README.md → docs/HANDOFF.md → CONTRIBUTING.md 순서로 읽는다.
2. 최신 main을 기준으로 작업 브랜치를 만든다.
3. 로컬 서버로 기존 예제를 실행하고 초기 결과인 20초 여유를 확인한다.
4. 아래 요구사항을 구현하고 수용 기준을 검증한다.
5. 문서를 갱신하고 PR로 제출한다. 앱 배포와 main 병합은 이 작업의 완료 조건에 포함하지 않는다.

```bash
git clone https://github.com/sleepyJK/sc1BdOptimizer.git
cd sc1BdOptimizer
git switch -c feat/target-block-link
python3 -m http.server 8000 --directory dist
```

이미 저장소를 사용 중이면 깨끗한 작업 트리에서 main을 최신화한 뒤 브랜치를 만든다. Windows 서버 실행 명령은 README를 따른다.

## 3. 사용자에게 제공할 동작

### 목표 설정 방식

타이밍 비교 패널에 다음 두 모드를 제공한다.

- **상대 블록 연결**: 상대 진영 블록 하나를 선택하여 그 블록의 완료 시각을 목표로 삼는다.
- **직접 입력**: 현재처럼 목표 시각을 분:초로 입력한다.

신규 예제와 '예제 초기화'는 상대 뮤탈리스크 블록 연결을 기본으로 한다. 기존 저장 데이터는 직접 입력 모드로 불러와 기존 목표 시각을 유지한다.

상대 블록 선택 목록에는 이름과 완료 시각을 함께 표시한다. 같은 이름이 여러 개 있어도 고유 ID로 구분한다. 내 블록은 선택 목록에 포함하지 않는다. 블록 이름 문자열을 비교하여 목표를 찾는 구현은 피한다.

### 연결 모드

- 목표 시각은 선택 블록의 `start + duration`에서 계산한다.
- 시작 시각 또는 소요 시간의 변경이 확정되면 목표 표시, 도착 기준선, 비교 결과를 함께 갱신한다.
- 폼 적용, 드래그 완료, 키보드 이동 모두 같은 계산 경로를 사용한다.
- 드래그 중 실시간 계산은 선택 사항이며, 드래그 완료 직후 일관성은 필수다.
- 연결 중 목표 시각 입력은 읽기 전용으로 표시하고 연결된 블록을 식별할 수 있게 한다.
- 이동 시간은 별도 값으로 유지한다. 뮤탈 생산 완료와 예상 도착을 구분하여 보여준다.

### 모드 전환과 삭제

- 연결 모드 → 직접 입력: 전환 직전 연결 블록의 완료 시각을 입력값으로 복사한다.
- 직접 입력 → 연결 모드: 이번 세션에 이전에 선택했던 유효한 상대 블록이 있으면 재사용한다. 없으면 블록 선택을 요구한다. 임의의 상대 블록을 자동 선택하지 않는다.
- 목표 블록 삭제: 연결 모드를 유지하고 선택값을 비운다. '상대 목표 블록을 선택하세요'를 표시하고 비교 결과와 도착 기준선을 숨긴다.
- 유효한 상대 블록이 없는 경우에도 위와 같은 빈 상태를 제공한다.
- 내 대응 블록이 없으면 '내 대응 항목을 선택하세요'를 표시한다. 목표가 유효하면 목표 기준선은 유지한다.
- 초기화는 예제 블록, 목표 뮤탈 연결, 기본 터렛 대응, 이동 시간 0초를 함께 복원한다.

## 4. 계산 및 상태 기준

내부 시간 단위는 정수 초를 유지한다.

```text
목표 완료 = 연결한 상대 블록의 시작 + 소요 시간
           또는 직접 입력한 목표 시각
예상 도착 = 목표 완료 + 이동 시간
내 대응 완료 = 대응 블록의 시작 + 소요 시간
여유 = 예상 도착 - 내 대응 완료
```

표시는 다음과 같이 명확히 구분한다.

| 여유 값 | 표시 |
| --- | --- |
| 양수 | 20초 여유 / 상대 도착보다 먼저 준비 |
| 0 | 동시 완료 |
| 음수 | 10초 지연 / 상대 도착보다 준비가 늦음 |
| 목표/대응 미선택 | 선택 안내, 숫자 결과 없음 |

권장 추가 상태는 `targetMode: "manual" | "block"`, `targetBlockId: number | null`이다. 기존 `target`은 직접 입력 모드의 값으로 유지할 수 있다. 연결 모드의 목표 시간은 매번 원본 블록에서 계산하여 두 개의 시간이 서로 어긋나지 않도록 한다.

현재 렌더 흐름에서 `target`은 패널 표시, 비교 계산, 기준선 위치, 시간축 길이에 사용된다. 네 곳 모두 같은 유효 목표 시간을 사용해야 한다. 선택된 목표가 없더라도 시간축 길이 계산에 NaN이 들어가면 안 된다.

전체 저장 구조 개편은 필요 없다. 기존 키 `buildlab-v1`에 선택한 모드와 블록 ID를 추가하여 저장한다.

- 새 필드가 없는 기존 데이터: manual 모드, targetBlockId=null로 해석한다.
- 기존 blocks, name, responseId, target, travel, nextId를 보존한다.
- block 모드인데 ID가 없거나 내 블록을 가리키면 선택 없음 상태로 복원한다.
- 이름만 같은 새 블록을 기존 목표로 자동 연결하지 않는다.
- 잘못된 targetMode는 manual로 해석한다.
- 전체 손상 데이터 복구는 후속 과제지만 이번 변경으로 기존 저장 데이터를 초기화하지 않는다.

## 5. 변경 범위

예상 변경 파일:

- `dist/index.html`: 목표 모드, 상대 블록 선택 UI와 안내
- `dist/app.js`: 목표 상태, 이벤트, 계산, 저장/복원
- `dist/style.css`: 추가 UI의 최소 스타일과 모바일 배치
- 필요 시 작은 순수 계산 모듈과 테스트 파일
- `docs/HANDOFF.md`: 구현 결과와 남은 제한 업데이트

유지해야 할 기능은 중앙 세로 시간축, 좌우 빌드, 생산 시간에 비례한 높이, 추가/삭제/검색/확대/메모/자동 저장이다.

이번 PR에는 프레임워크 전환, 자원/선행 조건 엔진, 실제 데이터 조사, A/B 비교, 연쇄 일정 이동, 로그인/서버 저장, 자동 배포를 포함하지 않는다. 게임상 비유효한 예제 수치는 그대로 두고 임의 데이터 안내를 유지한다.

## 7. 검증과 제출물

- 변경한 JS 파일의 구문 검사를 실행한다.
- 목표 계산, 여유의 양수/0/음수, 유효하지 않은 목표 ID, 기존 데이터 기본값에 대해 DOM과 무관한 테스트를 작성한다. 프로젝트 규모에 맞게 Node 내장 테스트 등 최소 구성을 선택한다.
- PC 브라우저에서 폼/드래그/키보드/새로고침 경로를 직접 확인한다.
- 390px 모바일 화면과 PC 화면에서 추가 UI가 잘리거나 좌우 타임라인을 깨뜨리지 않는지 확인한다.
- 실제 터치 기기를 사용하지 못했다면 '모바일 실기기 미검증'을 명시한다. 화면 크기 확인을 실기기 검증으로 기록하지 않는다.
- PR에는 변경 요약, 실행한 테스트 명령/결과, 수용 기준 확인표, 화면 캡처, 남은 제한을 첨부한다.
- HANDOFF에는 구현 완료와 미검증 부분을 구분해서 갱신한다.
