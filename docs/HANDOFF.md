## 1. 사용자 목표와 확정 요구사항

웹(PC·모바일)에서 스타크래프트 1:1 래더 빌드를 연구하는 서비스다. 핵심은 시간 단위의 빌드 최적화 연구이며, 사용자가 사전에 조사한 실제 데이터는 추후 제공 예정이다. 현재는 데이터를 조사하거나 정확성을 가정하지 말고 임의 값을 사용한다.

중앙에 세로 시간축을 두고 좌우에 두 플레이어의 건물·유닛 생산을 배치한다. 블록 높이는 소요 시간에 비례한다. 대표 시나리오는 오른쪽에 5분 30초 뮤탈 빌드를 두고 왼쪽에서 대응 빌드를 설계하는 것이다.

이번 단계는 타이밍 편집 UX를 확인하는 프로토타입이다. 자동 최적화 엔진, 후속 일정 연쇄 이동, A/B 비교는 제안 단계이며 확정 구현 요청이 아니다.

## 3. 실행과 기술 구조

README의 Python 정적 서버 명령으로 실행한다. 런타임은 브라우저 JavaScript이며 프레임워크, 백엔드, 외부 API, 데이터베이스, 패키지 설치 또는 번들러는 없다. `dist/`의 세 파일이 원본이다.

`app.js`는 현재 함수와 이벤트 핸들러를 압축된 형태로 한 파일에 담고 있다. 공동작업을 시작하면 동작을 유지하면서 포맷 정리와 데이터/계산/저장/뷰 분리를 별도 PR로 진행하는 것이 좋다.

| 함수/상태 | 역할 |
| --- | --- |
| `data` | 종족별 예제 카탈로그: 이름, 소요 초, 종류, 문자 아이콘 |
| `seed()` | 최초 예제 15개 블록과 기본 비교값 초기화 |
| `renderCatalog()` | 종족/검색/종류 필터, 항목 추가 |
| `lanes(items)` | 시작 시간 순으로 겹치지 않는 표시 열에 배치 |
| `render()` | 시간축·블록·비교 결과·편집 폼 재생성 후 저장 |
| `save()` | localStorage 직렬화 |
| `fmt()` / `parse()` | 초 ↔ 분:초 변환 |
| `selected`, `side`, `filter`, `scale` | 선택 블록, 추가 대상, 필터, 초당 픽셀 |
| `responseId`, `target`, `travel`, `nextId` | 대응 블록, 목표 초, 이동 초, ID 발급값 |

## 4. 데이터 구조와 시간 규칙

블록 예시:

```json
{
  "id": 9,
  "side": "me",
  "name": "미사일 터렛",
  "start": 280,
  "duration": 30,
  "note": ""
}
```

`side`는 `me` 또는 `enemy`다. 모든 내부 시간은 정수 초이며 현재 화면은 `분:초`로 표시한다. 별도 시:분:초 표기와 게임 프레임/게임 속도 환산은 없다. `name`은 표시 이름으로, 엔티티 ID·종족·생산 건물·선행 조건은 블록에 저장하지 않는다.

완료 시각은 `start + duration`이다. 비교 여유는 다음과 같다.

```text
여유 = target + travel - (대응 블록 start + duration)
```

양수 여유는 현재 UI에서 `−20초`처럼 표시한다(상대보다 20초 먼저). 음수 여유는 `+10초`처럼 표시한다(10초 늦음). 0초도 현재는 '먼저 준비됩니다'와 `−0초`로 표시하므로 별도 동시 완료 문구가 필요하다.

- 기본 예제: 뮤탈 04:50 시작, 40초 생산, 05:30 완료.
- 기본 터렛: 04:40 시작, 30초 생산, 05:10 완료 → 20초 여유.
- 폼의 시작 시각은 0~7200초, 소요 시간은 1~600 정수 초로 검사한다.
- 목표 시각은 분:초 형식, 최대 7200초. 이동 시간은 0~300초로 제한한다.
- 드래그는 5초 간격으로 반올림하며 음수 시작을 막는다. 키보드 위/아래는 1초, Shift 조합은 10초 이동이다.
- 드래그/키보드/추가 경로에는 폼과 동일한 최대 시작 시간 제한이 없다.
- 새 항목은 해당 진영의 가장 늦은 완료 시각 뒤에 붙는다. 원하는 시각에 직접 드롭하여 추가하는 기능은 없다.
- 시간축 기본 눈금은 30초, 확대는 초당 2/3/4픽셀이다.
- `lanes()`는 표시 겹침을 피하는 로직이다. 생산 시설별 대기열이나 게임상 동시 생산 가능 여부를 판단하지 않는다.

## 5. 저장 구조

localStorage 키: `buildlab-v1`

저장 필드: `blocks`, `responseId`, `target`, `travel`, `name`, `nextId`.
선택 블록, 필터, 확대, 종족 선택 UI 상태는 저장하지 않는다. 새로고침 시 첫 내 블록을 선택한다. 하나의 연구만 보관하며 저장 슬롯·버전 이력·공유·서버 동기화·내보내기 기능은 없다.

시작 시 저장값 파싱 실패는 무시하지만, 구조 검사는 `blocks`가 배열인지 정도에 그친다. 손상 데이터의 각 필드 타입/범위/ID 중복 검증과 스키마 버전·마이그레이션은 필요하다. 메모와 시작/소요 편집은 '변경 적용'을 눌러야 반영된다. 다른 동작이 `render()`를 호출하면 적용 전 폼 입력이 덮어써질 수 있다.

## 9. 공동작업 시 지킬 기준

핵심 화면인 중앙 세로 시간축과 좌우 비교를 유지한다. 추후 프레임워크 변경은 데이터/시간 계산과 UI를 분리한 뒤 별도 결정한다. 임의 값을 실제 게임 데이터로 표시하지 않는다. 기능 변경 PR에는 테스트 방법과 남은 제한을 기록한다. 실제 조사 데이터는 아직 전달되지 않았으므로 임의로 정확한 값이라고 교체하지 않는다.

사이트 배포용 인증 정보, Git 토큰, 사용자 브라우저 데이터는 저장소에 포함하지 않는다. `.openai/hosting.json`의 ID는 기존 배포 연결 정보다. 기존 사이트 갱신은 해당 접근 권한을 가진 소유자가 진행하며, 다른 사이트로 복제할 때 기존 ID를 재사용하지 않는다.
